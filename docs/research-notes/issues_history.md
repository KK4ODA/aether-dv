# D-RATS ecosystem: historical bugs, failure modes, and modernization attempts

Research notes for the architecture study of a new D-RATS-compatible D-STAR data app.
Compiled 2026-10-29.

## Sources and method

- GitHub issue and PR pages for `ham-radio-software/D-Rats` (226 issues, 90 PRs), `ham-radio-software/drats2` (13 open issues, 8 merged PRs, 5 wiki pages), `ham-radio-software/ratflectors` (0 issues), `w9fyi/macrats` (0 issues). ## (a) RF transport, serial, and radio problems

**XON/XOFF handling lost bytes; this is the single most important RF bug.**
- [DR#253](https://github.com/ham-radio-software/D-Rats/issues/253), "Serial port XON/XOFF handling totally broken" (2023-10, Reproduced). Symptoms over RF only: file list and position requests time out, ACK timeouts, `Checksum failed`, and a stray `0x11` at the start of GPS frames. Ratflector paths worked between the same versions. WB8TYW's root cause, which also applies to the **0.3.x Python 2 code**: after transmitting, `SWFSerial` assumed the radio had sent XOFF, waited for one byte, and **discarded any byte that was not XON or XOFF**. There was no real detection of a radio XOFF, and pyserial's `xonxoff` was explicitly disabled for unknown reasons. Log signature: `SWFSerial:is_xon: Assuming IXANY behavior`.
- The first fix moved to driver XON/XOFF (shipped in 0.4.2 as "Use serial driver XON/XOFF Handling (#253)"). Then [DR#262](https://github.com/ham-radio-software/D-Rats/issues/262) (Icom ID-5100 / ID-51 / IC-2820 stations mixing 0.3.10 and 0.4.1.dev) showed that 0.4.1.dev stations could not receive chat. WB8TYW found the driver was running in Linux IXANY mode, which requires the sender to keep re-sending XOFF, and radios do not. PR #268 ("More XON/XOFF fixes", 2023-11-07) **reverted to software XON/XOFF** but stopped discarding non-flow-control bytes, and added a `--sdebug` serial capture option. NEWS.rst therefore misdescribes the final 0.4.2 state.
- [DR#252](https://github.com/ham-radio-software/D-Rats/issues/252), "Download issue (on radio)" (open). RPC `Request file None`, `Block has no header/trailer`, checksum mismatch. Attributed to the same byte-drop bug.
- [DR#132](https://github.com/ham-radio-software/D-Rats/issues/132), "Serial port enhancements needed" (open since 2022). Covers 3-wire radio cables (Icom ID-51 family has TX/RX/GND only), RTS/CTS, DTR/DSR/CD monitoring, and KISS's inability to use software flow control. In 2025 dscp46 (F4HOF) reported that relying on **OS-level software flow control** fixed the same problem in his `dvtnc` project. WB8TYW confirmed that D-Rats expected the first byte read into an empty buffer to be XOFF.

**Threading and half-duplex design**
- [DR#134](https://github.com/ham-radio-software/D-Rats/issues/134), "Transport should have separate worker threads for transmit and receive" (open). A single worker thread forces **polling reads**. The full fix for reconnect bugs (#109) depends on it.
- [DR#261](https://github.com/ham-radio-software/D-Rats/issues/261), "File Sending Slow": a 143 kB file over Internet ratflector was unusably slow. Maintainer answer: the client is **half-duplex by design, even over TCP**, unchanged since 0.3.
- [DR#315](https://github.com/ham-radio-software/D-Rats/issues/315) (WB8TYW comment, 2026-04): GTK's limits are blocking "handling serial and network ports as half duplex" correctly. The **file transfer protocol has a bug that can leave files stuck in a pending state**.

**Timeouts, warmup, pacing**
- [DR#114](https://github.com/ham-radio-software/D-Rats/issues/114): `d-rats_repeater` ignored the serial warmup timeout (fixed in 0.4.0).
- Source finding: `transport.py` sends a warmup frame (type 254, src and dst `"!"`, payload `0x01` × `warmup_length`, uncompressed) only if `time since last TX > warmup_timeout` **and `warmup_timeout > 0`**. Since 0.3.6, `config_defaults.py` sets `warmup_length=16` and **`warmup_timeout=0`**, so **warmup is disabled by default**. The docstring also calls `warmup_length` "seconds", but it is a byte count.
- Stateful session (`sessions/stateful.py`): blocksize 1024, ACK timeout = max(12 s, 1.5 × pending/rate), REQACK backoff `4 + attempts*4` s, retry cap, and 8-bit block sequence numbers.
- [DR#148](https://github.com/ham-radio-software/D-Rats/issues/148): a Windows (mingw64) `SerialTimeoutException` write timeout, followed by `PermissionError` on reconfigure. The port wedges until the USB cable is replugged.
- [DR#166](https://github.com/ham-radio-software/D-Rats/issues/166): Windows "semaphore timeout period has expired" during port enumeration.

**yEncode, CRC, and D-STAR slow-data pitfalls**
- [DR#305](https://github.com/ham-radio-software/D-Rats/issues/305) and PR [#303](https://github.com/ham-radio-software/D-Rats/pull/303) by dscp46/F4HOF (2025-03). Per **JARL STD6 §6.2**, the byte run `0xE7 0x84 0x76` in DV slow data, when the voice field carries the silence pattern (`9E 8D 32 88 26 1A 3F 61 E8`), is interpreted by receivers as **packet loss**, so data is dropped. Fixed in #302 by extending the yEncode banned set. The current `DEFAULT_BANNED` is `11 13 1A 00 84 E7 FD FE FF C0 DB` plus `=` (escape = `'='` + (b+64) mod 256). Backward compatible: decoders do not consult the banned list. Comments in the code: `0xFD` might be "Icom switch to radio control mode?", `0xFF` unknown, and `C0/DB` are KISS FEND/FESC.
- PR #302 also fixed **Python 3 str-vs-bytes corruption** in `agw.py`, `comm.py` and `wl2k.py` (see (c)).
- DDT2 CRC: CRC-16 table in `comm.py`. Frames are wrapped `[SOB]…[EOB]`. Header checksum mismatches appear in logs (`Checksum failed: 1170 != 36670`) whenever bytes are dropped.
- [DR#306](https://github.com/ham-radio-software/D-Rats/issues/306) (open, Reproduced): a station heard via radio is not listed when the radio's GPS has **no fix**. Radio-injected NMEA with empty fields breaks float parsing, so the trailing 8-char callsign and 20-char message are never extracted. There are **two separate GPS parsers** (transport vs `gps.py`). The maintainer deferred the rework to drats2.

**Specific radios and ports**
- [DR#263](https://github.com/ham-radio-software/D-Rats/issues/263), IC-9700 stuck in TX. The driver creates two COM ports, so use the one **not** used by the programming software. The radio must be in DV mode, at 9600 baud.
- Wiki page "030 Connecting D-Rats with a D-Star radio": 9600 baud for most Icom radios, 38400 for IC-91AD/92AD/2820 (UT-123), 19200 for ID-1. Typical settings are "DV data TX = Auto" and GPS TX off. **Fast Data** only works ID-51A Plus ↔ ID-51 Plus / ID-5100 (updated firmware). There is no Kenwood entry.
- [DR#316](https://github.com/ham-radio-software/D-Rats/issues/316) (open, no maintainer reply): TH-D74/D75 recipe from MacRats. **Menu 614 "Data TX End Timing" = Off silently disables data auto-TX.** Menu 984 must match USB or Bluetooth.
- F4FXL report (https://www.f4fxl.org/buggy-icom-id-51-and-id-5100firmware/): ID-51 E3 firmware (late 2019) **switched to Fast Data when sending GPS** and omitted the end-of-transmission frame. Fixed in the Dec 2019 ID-51 Plus2/5100/4100 firmware.
- Serial enumeration: [DR#309](https://github.com/ham-radio-software/D-Rats/issues/309) and [DR#310](https://github.com/ham-radio-software/D-Rats/issues/310) (`/dev/ttyACM*` missing for the TH-D74 on Ubuntu 24.04), PR [#308](https://github.com/ham-radio-software/D-Rats/pull/308), PR [#311](https://github.com/ham-radio-software/D-Rats/pull/311) (`/dev/rfcomm*` for Bluetooth to an IC-4100). All were superseded by #314 (2026-08), which uses `serial.tools.list_ports`. Also [DR#301](https://github.com/ham-radio-software/D-Rats/issues/301) (antiX serial error with an IC-2820), [DR#255](https://github.com/ham-radio-software/D-Rats/issues/255), [DR#258](https://github.com/ham-radio-software/D-Rats/issues/258) (macOS serial config errors), and [DR#269](https://github.com/ham-radio-software/D-Rats/issues/269) (radio port config is a **comma-delimited string**: a comma in a name corrupts the config, and there is no room for flow-control attributes).
- AX.25/AGWPE: [DR#298](https://github.com/ham-radio-software/D-Rats/issues/298) (I-frames `0x3E` sent instead of UI `0x03`), [DR#112](https://github.com/ham-radio-software/D-Rats/issues/112) (AGW header mismatch), PR [#300](https://github.com/ham-radio-software/D-Rats/pull/300) (callsign shift-left encoding produced 4 UTF-8 bytes for "CQ"), [DR#116](https://github.com/ham-radio-software/D-Rats/issues/116), [DR#41](https://github.com/ham-radio-software/D-Rats/issues/41) (KISS docs), [DR#25](https://github.com/ham-radio-software/D-Rats/issues/25) (RS-MS1A integration: no protocol definition).
- Self-addressed traffic is dropped as a loop, so a file or form sent to yourself stays locked forever (PR #300 thread, [DR#122](https://github.com/ham-radio-software/D-Rats/issues/122)).

## (b) Ratflector and network problems

- **Silent disconnect and no reconnect.** [DR#75](https://github.com/ham-radio-software/D-Rats/issues/75) (open since 2020: retry every ~60 s), [DR#109](https://github.com/ham-radio-software/D-Rats/issues/109) (open; partial fix in 0.4.0, "fixed" label later removed), [DR#142](https://github.com/ham-radio-software/D-Rats/issues/142) (dup), [TYW#154](https://github.com/wb8tyw/D-Rats/issues/154) (Windows 7). Root cause: a closed socket returns 0 bytes, which the **half-duplex polled read cannot distinguish from idle**. ISP/NAT idle timeouts kill quiet TCP sessions, and the only workaround is a timed QST. **There is no keepalive in the protocol.**
- **Status UI lies.** [DR#234](https://github.com/ham-radio-software/D-Rats/issues/234) shows "Online" while connection-refused: status is the user's *intended* presence, not link state. Also [DR#74](https://github.com/ham-radio-software/D-Rats/issues/74), [DR#100](https://github.com/ham-radio-software/D-Rats/issues/100), [DR#130](https://github.com/ham-radio-software/D-Rats/issues/130), [DR#131](https://github.com/ham-radio-software/D-Rats/issues/131) ("Connected to Internet" toggle not working).
- **Auth.** [DR#201](https://github.com/ham-radio-software/D-Rats/issues/201): Py3 client `do_auth()` sent `str` to the socket (TypeError). The repeater logged `User None failed to authenticate` and the client showed `201 Protocol violation / 500 not authorized`. Fixed by #202 (0.4.2). [DR#240](https://github.com/ham-radio-software/D-Rats/issues/240): "Conversation error" with auth enabled. Handshake per `comm.py`: server line `100` = no auth; `101` → client `USER <call>\r\n`; `102` → `PASS <pw>\r\n`; `200` ok; anything else fails. A non-numeric or absent banner makes the client assume an "old-school" ratflector and proceed. Quirk: if the server answers `200` to USER, the client still sends PASS. **Plaintext only.**
- **Multi-ratflector routing.** [DR#71](https://github.com/ham-radio-software/D-Rats/issues/71): a callsign "moves" between ratflectors because D-Rats remembers only the **last port a call was heard on**, persisted for message routing. Related: [DR#70](https://github.com/ham-radio-software/D-Rats/issues/70), [DR#73](https://github.com/ham-radio-software/D-Rats/issues/73), [DR#40](https://github.com/ham-radio-software/D-Rats/issues/40) (send to all ports), [DR#77](https://github.com/ham-radio-software/D-Rats/issues/77) (persistent chat buffers on reconnect). No duplicate-suppression or loop issues were filed beyond the self-send loop drop.
- **Repeater (d-rats_repeater) coupling to GTK.** [DR#241](https://github.com/ham-radio-software/D-Rats/issues/241) (must run as a service without GTK), [DR#176](https://github.com/ham-radio-software/D-Rats/issues/176) (tries X11 in console mode), [DR#172](https://github.com/ham-radio-software/D-Rats/issues/172), [DR#146](https://github.com/ham-radio-software/D-Rats/issues/146) (saves config in `sig_destroy`), [DR#243](https://github.com/ham-radio-software/D-Rats/issues/243) and [DR#251](https://github.com/ham-radio-software/D-Rats/issues/251) (repeater crashes; GPS TypeError), [DR#231](https://github.com/ham-radio-software/D-Rats/issues/231) (defaults to a real callsign), [DR#250](https://github.com/ham-radio-software/D-Rats/issues/250) (refuse root), [DR#242](https://github.com/ham-radio-software/D-Rats/issues/242) (wants a web management UI), [DR#232](https://github.com/ham-radio-software/D-Rats/issues/232) (log file transfers). A Python 2 repeater on 0.3.x keeps interoperating ("Allow d-rats repeater on python2", 2021-08).
- **Public ratflector discovery.** [DR#9](https://github.com/ham-radio-software/D-Rats/issues/9) and [DR#121](https://github.com/ham-radio-software/D-Rats/issues/121) (standard for downloaded config data) led to the `ratflectors` YAML repo (2023-03). It is not yet consumed by D-Rats itself; MacRats does fetch it. The old default `ref.d-rats.com` is effectively gone: **d-rats.com was hijacked or redirected** ([DR#295](https://github.com/ham-radio-software/D-Rats/issues/295), 2024-11), and the project never controlled the domain.
- drats2 proposals: [D2#13](https://github.com/ham-radio-software/drats2/issues/13) (per-packet **BLS short signatures**, ~20 bytes, replacing ratflector passwords, stripped for legacy clients), [D2#15](https://github.com/ham-radio-software/drats2/issues/15) (licensed/unlicensed mixed operation via callsign suffix conventions; the 8-byte station field is `CALL-SSID`), [D2#10](https://github.com/ham-radio-software/drats2/issues/10) (HTTP UI), [D2#11](https://github.com/ham-radio-software/drats2/issues/11) (systemd service), [D2#12](https://github.com/ham-radio-software/drats2/issues/12) (admin email), [D2#16](https://github.com/ham-radio-software/drats2/issues/16) (archiving robot for missed messages).

## (c) Protocol compatibility between versions (Py2 0.3.x vs Py3 0.4.x)

- **File size endianness.** [DR#111](https://github.com/ham-radio-software/D-Rats/issues/111) / [TYW#124](https://github.com/wb8tyw/D-Rats/issues/124): the file and form offer size was packed in *native* order, while all other DDT2 integers are big-endian. The resolution **freezes it as little-endian** (`struct.pack("<I", len)` in `sessions/file.py`), so the de facto standard is the x86 behavior. The wl2k and AGWPE fields are also little-endian.
- **str/bytes corruption in the Py3 port.** In 2021-03 WB8TYW fixed bytearray handling for ddt2 compression, rpc, chat and files. [TYW#70](https://github.com/wb8tyw/D-Rats/issues/70): the file list was empty because of a `.decode` on a `str`. [DR#252](https://github.com/ham-radio-software/D-Rats/issues/252) shows `NoneType.decode` in RPC. [DR#298](https://github.com/ham-radio-software/D-Rats/issues/298) and #302 found `chr(ord(x)<<1)` AX.25 address encoding and the `wl2k` header `chr(len & 0xFF)` being UTF-8-encoded, which turns high bytes into multibyte sequences. Audit result: `yencode`, `aprs_dprs`, and `gps` are clean.
- **XON/XOFF behavior differs 0.3 vs 0.4.** See [DR#262](https://github.com/ham-radio-software/D-Rats/issues/262). Mixed-version RF nets failed in one direction until #268.
- **Message/forms storage.** Forms are XML files (libxml2 replaced by lxml in 2021). [DR#76](https://github.com/ham-radio-software/D-Rats/issues/76): 0.3.10beta1 wrote 0-byte `form_*.xml` that crashed the inbox. [DR#175](https://github.com/ham-radio-software/D-Rats/issues/175): a non-XML (xlsx) file in the Inbox raises an exception at start. [DR#228](https://github.com/ham-radio-software/D-Rats/issues/228): attachment fails to validate on decompress. [DR#215](https://github.com/ham-radio-software/D-Rats/issues/215): form save/send/print broken. [DR#89](https://github.com/ham-radio-software/D-Rats/issues/89): `xmlParseMemory` failures. **No pickle use exists** in the current tree (grep). The wire carries DDT2 + zlib, and forms travel as XML file transfers.
- **Position format.** [DR#211](https://github.com/ham-radio-software/D-Rats/issues/211): position replies (APRS-style `$$CRC` strings) were mis-parsed on receive, about 20 miles off (decimal vs DMS). Fixed in #219. In 2020 the 0.3.9 format was changed "to be compliant with DPRS interface".
- **Packet-loss pattern and banned bytes.** See (a). Adding bytes to the banned set is decode-compatible with all older versions.
- **Callsign/SSID semantics.** The 8-byte station field is padded with `~`. D-Rats expects `-` before the SSID ([D2#15](https://github.com/ham-radio-software/drats2/issues/15), [DR#235](https://github.com/ham-radio-software/D-Rats/issues/235), [DR#140](https://github.com/ham-radio-software/D-Rats/issues/140) where the email gateway ACL requires `CALL-SSID`).
- WB8TYW (DR#315, 2026-04): **no plans to change DDT2**, and there is **no formal state diagram or protocol document**. A third party (dscp46) wrote a Wireshark dissector.

## (h) The drats2 rewrite

- **Plan** (README, wiki "00100 Roadmap", "00200 Rewrite of D-Rats communication package", "00103 Phase 3 user stories"). Goals: cross-platform, standards-compliant, native Windows, **remove the GTK dependency and allow alternative GUIs**, and test D-Rats internals properly. Structure: a multi-package repo of pip-installable packages (`drats_common`, `drats_gtk`, `drats_kivy`, `drats_text`, `drats_tk`, `drats_wx`, `repeater`, `version_git`), YAML config, Sphinx docs, towncrier, gettext with UPPER-CASE message tags.
- Phases: (1) hello-world packaging and testing infrastructure; (2) ratflector packaged for Linux as a service; (3) basic text messaging (MVP: config, multi-ratflector, multi-serial, online/offline, ping/ping-all, position request, **chat with old D-RATS clients over radio and ratflector**, activity log); (4) files and forms; (5) mail, Winlink, maps.
- **Toolkit evaluation** (developers_notes.txt, hello-world tests on Win11, MSYS2, MobaXterm, Ubuntu 22.04, Raspbian Bookworm, Fedora 41):
  - **Tkinter and wxPython worked everywhere tested.**
  - GTK4: not available natively on Windows, noisy on MSYS2 (falls back to GTK3), OK on Linux.
  - Kivy: works on native Windows and Linux, but not on MSYS2 or MobaXterm; needed for Android. Its own Logger forces a logging redesign.
  - `drats_text` is a terminal UI kept mainly for automated testing.
  - **No single toolkit was chosen.** The stated intent is a GUI-agnostic core with multiple front ends. WB8TYW in DR#315 (2026-04) described drats2 as "text-based design that enables unit testing and multiple GUI options."
- **What exists:** about 1,900 lines of Python in total, all hello-world windows, `version_git`, `common_args`, a `language` helper, and a 121-line `repeater_configure.py` stub. There is **no DDT2, transport, session, or serial code at all**. Twelve of the 13 open issues are packaging or ratflector wish-list items.
- **Why it stalled:** the last commit was 2025-03-22. The notes record months spent on "boring boiler plate" (hatch abandoned for setuptools, towncrier, Sphinx, MSYS2 unable to build packages, Kivy logging), with the author pivoting to the ratflector because boilerplate "does not seem to be making visible progress". In 2026-04 WB8TYW reported "a cascade failure of the test and development systems" that delayed the YAML config work. There is effectively one active developer, with no Windows or macOS packaging expertise ([D2#20](https://github.com/ham-radio-software/drats2/issues/20)). Fixes keep being deferred from D-Rats to drats2 (GPS parser [DR#306](https://github.com/ham-radio-software/D-Rats/issues/306), the mail rewrite [DR#296](https://github.com/ham-radio-software/D-Rats/issues/296)), so 0.4.x is in maintenance-only mode.
- Earlier modernization attempts: [DR#47](https://github.com/ham-radio-software/D-Rats/issues/47) "Major Upgrade?" (2020) discussed CHIRP's move to wxPython and decoupling the GUI before porting, but the GTK3 path won by default. The DigitalHERMES/d-rats fork is a stale Python 2.7 copy. One early refactor shipped in 0.4.0: the plugin server moved to a dynamic port.

## (i) MacRats (w9fyi/macrats, AI5OS Justin Mann)

- Swift/SwiftUI, GPL-3, about 8,800 lines in `MacRatsCore`, 249 tests. It was built in 4 days (2026-04-06 to 04-09, 25 commits). It describes itself as clean-room "faithfully ported from upstream Python". There are no GitHub issues yet.
- **Implemented:** DDT2 encode/decode (25-byte header: magic `0xDD` zlib / `0x22` raw, BE seq u16, session, type, BE CRC-16 computed with the field zeroed, BE length, 8-byte `~`-padded src/dst), `[SOB]…[EOB]` + yEncode with the **post-#302 banned set**, a frame splitter for chunked input, the warmup frame, chat/ping/status sessions, the APRS `$$CRC` GPS beacon, `StatefulSession` (T_DAT/T_ACK/T_REQACK, sliding window, 8-bit seq, 10-retry cap), file transfer (LE u32 size + filename offer, `OK`/`RESUME:`, zlib stream), and a ratflector client with the public directory.
- **Golden vectors** (from upstream Python): uncompressed `seq=3,session=2,type=1,FOO→BAR,"This is a test"` = `2200030201b557000e464f4f7e7e7e7e7e4241527e7e7e7e7e5468697320697320612074657374`. The compressed Python vector `dd00030201c3ab0014…78da0bc9c82c5600a2448592d4e21200247304f6` decodes, but **Apple's Compression deflate is not bit-identical to `zlib.compress(…, 9)`**, so senders cannot be byte-compared on compressed frames. Tests use decode equivalence.
- **Hardware discoveries:**
  - TH-D75 **Menu 614 Off silently disables fast-data TX** (no error, bytes vanish).
  - **Menu 984** routes DV/DR data to exactly one of USB or Bluetooth.
  - Bluetooth: the macOS `/dev/cu.TH-D75` device **does not carry DV data**. The transport must open an IOBluetooth **RFCOMM channel 2** directly. On macOS 26 Tahoe, `openRFCOMMChannelSync` fails and the async API is required, plus an `NSBluetoothAlwaysUsageDescription` TCC prompt.
  - USB CDC-ACM needs **DTR asserted** or the radio stays silent. Use `TIOCEXCL`, `POLLHUP` detection, and raw 8N1.
- **Contradictions and caveats vs D-Rats docs or its own docs:**
  1. The README claims the USB transport "speaks the G4KLX MMDVMHost protocol… stuffs DDT2 bytes into 3-byte slow-data slots". But the working recipe sets **Menu 650 (DV Gateway/terminal) = Off**, and the source only uses `MMDVMProtocol` in the `macrats-probe` tool. **The real path is raw DDT2 bytes to the radio's DV data serial port, the same as D-Rats.** MMDVM is future reflector work.
  2. MacRats **disables all serial flow control** (`IXON/IXOFF` off, no CRTSCTS), while D-Rats uses software XON/XOFF and escapes 0x11/0x13 precisely because radios assert them. RX from a real radio peer is **untested** ("Phase 3 needs a peer"), so throttling behavior on long transfers is unverified.
  3. MacRats emits a warmup frame after idle "matching transport.py exactly". But **stock D-Rats defaults (`warmup_timeout=0`) never send warmup**. That is harmless to receivers, but default airtime behavior differs.
  4. The User Manual (v0.1.0) says "No file transfer" and "Bluetooth awaiting live testing", while the README says both work. The manual's claim that MacRats "negotiates uncompressed framing" is inaccurate: DDT2 has no negotiation, just a per-frame magic byte.
  5. The ratflector handshake mirrors `comm.py` (100 / 101 → USER → 102 → PASS → 200 / 500, with a 5 s no-banner fallback to old-school mode). It was verified live against sewx.
  6. LZHuf (Winlink) is not implemented.
- Upstream engagement: [DR#315](https://github.com/ham-radio-software/D-Rats/issues/315) requested a `docs/PROTOCOL.md`, an accessibility note, and a discussion of a Toga/PySide6 port. The maintainer declined DDT2 changes and pointed to drats2. [DR#316](https://github.com/ham-radio-software/D-Rats/issues/316) (the TH-D75 recipe) has had no response.

## Cross-cutting lessons for a new implementation

1. Serial I/O must never discard bytes. Make flow control a per-port, explicit setting (none / software / OS-xonxoff / RTS-CTS), and keep yEncode escaping of 0x11/0x13 regardless.
2. Use full-duplex event-driven I/O with separate RX and TX paths, and explicit link-state detection (EOF = disconnect) with auto-reconnect and backoff. Show link state separately from presence status.
3. Treat ratflector TCP idle-timeouts as normal and design a keepalive that legacy peers tolerate (for example a periodic status frame that 0.3.x and 0.4.x ignore or accept).
4. Freeze wire quirks as spec: LE file-size field, `~` padding, the banned-byte set including `E7 84`, CRC-16 placement, type 254 warmup, and the auth line protocol. Build a golden-vector suite (MacRats has a start).
5. Structured config (not delimited strings), headless core and repeater, and an unprivileged service.
6. Parse radio-injected NMEA defensively. Expect empty fields and up to 3 sentences + 8-char call + 20-char message.
7. Handle radio-specific gotchas in onboarding: IC-9700 dual COM ports, TH-D75 Menu 614/984, TH-D74 `ttyACM`, Bluetooth RFCOMM, DTR assertion, and Fast Data compatibility limits.
